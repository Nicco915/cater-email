# 邮件自助操作闭环

更新日期：2026-11-04（第二轮修订）。本文定义业务发信人通过邮件自助完成补件、查询、重试与重新处理的规则，供业务与维护人员对照使用。实现位于 `src/cater/app`（intake / tasks / delivery / application / migrations 6 与 7），验收测试为 `tests/app/test_mail_ops.py`。

## 状态 × 命令矩阵

命令必须是新增正文中的独立一行；引用历史（`>`、`-----Original Message-----`、`On … wrote:` 等）中的指令一律不执行。发信人必须是任务原发起人且仍在当前白名单内。一封邮件只能包含一个指令，指令邮件不得夹带附件或字段修改；违反时不执行任何操作，并回信说明如何分开发送。同一封邮件（同 UID、同原文、同 Message-ID）被重复投递不会二次执行。

| 任务状态 | 查询状态 | 重试 | 确认重新处理 |
| --- | --- | --- | --- |
| 已收到 / 检查中 / 处理中 | 只读答复最新状态 | 拒绝并提示“正在处理，无需重试” | 拒绝并提示稍后或联系维护 |
| 结果待发送 | 只读答复 | 拒绝并提示无需重试 | 允许（新版本重交付） |
| 已完成 | 只读答复 | 拒绝并指引改用“确认重新处理”，绝不重复交付 | 允许（新版本重交付） |
| 等待补充资料 | 只读答复并列出当前缺项 | 不执行处理，按当前命令邮件单独回复具体缺项 | 允许（新版本重交付） |
| 技术重试中 | 只读答复 | 立即用当前版本与资料重试（新故障周期） | 允许 |
| 技术故障已暂停 | 只读答复 | 立即重试（新故障周期，可再获一次故障反馈） | 允许 |
| 发送结果待确认 | 只读答复并说明需人工核对 | 拒绝，不能绕过发送不确定性 | 拒绝，提示先核对发送结果 |
| 已取消 | 只读答复 | 拒绝，指引联系维护 | 拒绝，指引联系维护 |

通用规则：

- 关联只认 `[CATER task_xxx vN]` 主题标记、正文 `任务编号：task_xxx` 独立行、或对系统通知（References/In-Reply-To）的回复；多候选或冲突一律按歧义过滤，绝不按主题关键词猜测任务。
- 缺编号、编号未知或关联歧义的指令邮件：不创建任何业务任务、不执行任何操作，但会向发件人（须白名单内、非系统地址）持久化发送一封**无任务归属的通用指引**（发件箱用途 `guidance`，任务号为空）：请直接回复系统通知邮件，或新写邮件首行填 `任务编号：task_xxx`、第二行单独写指令。指引信同样走 dry-run / 白名单 / 发件箱持久化流程，同一邮件重投不重复发送，信内不含任何真实任务信息。
- 编号明确但发件人非原发起人：过滤不回显任务明细，只发送通用无权限指引（请原发件人本人操作），同样不产生业务任务。
- 被拒绝的命令会收到一封中文指引邮件（说明当前一件事、资料未改动、下一步与可复制示例）；相同原因与版本的去重，避免循环轰炸。
- “等待补充资料”状态下每次新的“重试”命令邮件都会得到一封单独的答复（列出当前具体缺项、说明暂时不能重试）；同一封邮件重投不重复答复。
- “查询状态”不复用为重新处理确认；查询只读：不重算、不加版本、不改状态与游标，查询邮件也不会成为核心处理请求的输入（业务邮件载荷始终取自原任务邮件）。重复投递同一查询邮件不重复通知；新查询邮件总能拿到最新状态。

## 技术故障的有限自动重试与通知

- 可恢复技术失败（核心不可用、核心异常、核心响应非法）最多自动重试 3 次，退避为 60 / 300 / 900 秒，次数与通知标记持久化在 `tasks.retry_count / failure_notified / failure_seq`，重启不重置、不重复通知。
- 达到上限后任务进入“技术故障已暂停”（FAILED），向原发起人持久化发送一封说明邮件，**按实际情况描述**：自动重试已多次尝试且已用完、您提供的资料已保存无需重发原邮件、可直接回复“重试”、持续失败请联系维护。邮件不含错误码、堆栈或主机路径。
- 一次性不可恢复失败（如已保存资料无法读取、配置/鉴权/磁盘错误）的说明邮件**如实描述**：第一次尝试即无法继续、未进行自动重试，请勿重复发送相同邮件以免产生重复任务；绝不虚称“连续多次”或“资料已全部保存”。
- 同一连续故障只通知一次；发起人主动“重试”开启新故障周期，再次失败可再获一次反馈（`failure_seq` 单调递增保证通知去重键唯一）。
- 不可恢复失败不消耗自动重试预算，直接暂停并通知一次。
- 崩溃恢复把中断任务放回重试队列（不计次数）；SMTP 自身不可用时通知留在发件箱按既有退避重试，不假称已送达。
- 全局 IMAP 等无任务归属的故障只记录在本地健康页（“上次全局收信异常”）与日志，不向任何客户群发。
- 发送结果待确认（SEND_UNKNOWN）的任务不能通过“重试”绕过，必须维护人员在管理页核对。

## 附件补件（同名替换）

- 原发起人直接回复正确的 Excel 即可继续，不需要填写目的国等任何额外字段；纯附件回复会创建新版本并继续处理。
- 新附件与原参与处理的附件同名（规范化：NFC、忽略大小写与空白）时，替换“参与本版本处理的输入”：旧版本输入行与旧文件原样保留，新版本只携带新文件，核心请求不会同时收到新旧同名文件。
- 不同名时的解决方式：**由发件人沿用原附件名重新回复发送该 Excel 即可**，系统会自动按同名替换处理，无需维护介入。系统回信会列出当前参与处理的附件名以便对照。
- 任务此前**没有保存任何 Excel 附件**时（例如原始邮件只有不支持的文件）：单独一份可识别的 Excel 会被接受为首次补供，正常进入新版本处理；一次发送多份不同名附件因无法判别各自角色而全部暂停，回信说明请分次发送、每次沿用对应原附件名。只有当角色确实无法判定时才需要维护人员人工介入。
- 同一邮件多份同名但内容冲突的附件、超限附件、写盘失败：一律不改动任何数据（先暂存、全部校验通过后才建新版本），并回信说明。
- `.eml/.msg` 原文仅作审计证据，永远不会被当作可替换的业务 xlsx；替换仅针对业务输入，审计原件不删除。

## 补件提交的原子性

- 提交分两个阶段：先把暂存附件**全部可靠落盘**到未来版本目录；再在**单一数据库事务**内完成国家别名（含审计行）、新版本、目的国、字段覆盖与新输入行。任一阶段失败：回滚数据库（旧活动版本、旧输入、国家配置保持原样），删除本次产生的未引用文件与暂存目录，任务回到可补状态，发件人可原样重发同一补件。
- 故障注入测试（第二个文件落盘失败、输入行写入失败）验证：版本、输入、目的国、别名均不变，重发同名补件可正常完成。
