# 第二阶段：批次持久化、人工确认与幂等创建逐票任务

## 角色与任务范围

用户已授权继续下一阶段，指定 Claude Code 写代码、Codex 制定计划/监控/审核。需要用户业务判断时必须停止相关工作，通过 Orca ask 向协调者提问，等待明确答复，不能代替用户猜测。完成后 worker_done 给出证据，非零测试不能当成功。当前 checkout 协作，无提交/推送。

在第一阶段离线预览基础上，实现完整可操作闭环：本地导入 EML -> 持久化批次/方案 -> Web人工确认/处理归属 -> 幂等创建逐票任务。此阶段不接自动收信、不运行正式核心转换、不生成报关表、不交付邮件。

## 设计要求

### 1. 持久化模型与审计

追加新迁移（现最高13，执行前确认），不改已应用迁移。推荐 mail_batches、batch_plan_versions、batch_candidates、batch_assets、batch_tasks、batch_events 或等效精简结构。

- 邮件原件/原始附件不可变保存一次，明确原始投递身份与内容指纹，文件哈希与来源定位。
- 邮件身份和内容去重要分层：同一原邮件重复导入/并发导入不建重复批次；不同邮箱/owner/原文不能只因附件相同误复用同一批次；source_fingerprint 包含识别器/规则版本，不可作为唯一永久邮件身份，否则规则升级会重复建批次。
- 每次方案调整/重新识别建立新版本，保存不可变预览JSON、识别器/别名标记、来源指纹与调整审计；不覆写旧版本。
- 批次与单票任务使用关联表，一对多。保留 legacy mail_messages.task_id 兼容旧单票流程，不能把某个任意子任务写作多票唯一归属。
- 身份采用独立存储ID，明确候选内容寻址ID、批次ID、单票任务ID的不同含义。

### 2. 本地导入与 Web 界面

- CLI提供显式离线批次导入/查看（命名自行与现有CLI风格保持一致），第一阶段 preview-tickets 继续无DB/无凭据副作用。
- Web增加批次列表/详情，展示方案版本、候选、附件与区域来源、机器归属、金额/数量/重量核对、阻断项、未归属正文行/附件、确认记录及关联任务。
- 上传采用本地 .eml 文件上传，不接受网页提交任意服务器文件路径。限制流式或受限读取字节/附件数量/解包大小；复用现有安全/来源模型。
- 所有变更POST走现有CSRF、Origin/Host/会话校验；HTML自动转义，文件下载受批次归属校验，不暴露任意路径。使用现有Jinja/CSS，无新前端依赖。
- 不要做只有JSON编辑器的界面：提供明确候选选择、来源归属/排除和问题说明表单。可用结构化调整能力实现范围内的“把未归属正文行/附件指派到唯一候选或有理由排除”；重新核对产生新方案版本。
- 不能靠客户端提交 candidate facts/路径/owner 来创建任意输入；所有选择必须服务端从存储版本和真实材料校验。

### 3. 确认边界与冲突策略

- batch_ready 只表示预览无阻断，人工必须明确确认具体方案版本/指纹/所选候选，不能自动确认。
- 未归属业务正文行和非装饰附件必须显式指派或排除（理由和actor审计）；非业务内嵌图片可以默认作为审计材料，但不得默认忽略无法读取的Excel。
- 多个候选共用正文表时，每行必须精确归属；若共用文件只作证据，需要明确角色，不能让全部业务内容进每个任务。
- 数值/身份冲突不得用一个“忽略全部”按钮清除。允许有证据的服务端重新关联/选择材料版本并重新核对；否则保留阻断，不能确认/建任务。金额、毛重、最终目的国等业务问题没有依据时使用 ask，不猜测、不得自动按文件顺序取胜。
- 每个候选允许显式选入或排除（有理由）；未解决问题的候选不能选入建任务。所选候选非空。未选候选状态明确保存，不能悄悄丢票。
- 乐观锁：旧页面/旧方案的确认、并发修改必须拒绝或幂等返回，不得确认错误版本。已物化的批次本阶段不得再次改方案/额外建票（有明确immutable约束），避免跨方案重复任务。

### 4. 幂等创建任务及输入快照

- “确认并创建任务”以一个明确操作提交：同一事务校验当前方案/确认条件，创建所选子任务、版本、来源关联、隔离输入快照与batch_tasks；重复点击/并发/重启后相同请求只返回既有同一组任务，唯一约束兜底。
- 附件可靠落盘先于DB提交；失败必须回滚任务/确认/关联，不留下半批可执行任务。若进程崩溃可能产生未引用暂存文件，记录并提供安全清理/恢复策略。
- 不嵌套 BEGIN（TaskRepository.create 自带事务）；需要可组合的事务内创建方法或等效合理重构，旧单票行为和事件保持兼容。
- 每票固化自己的附件哈希/版本、来源区域和精确正文行快照；原始父邮件仅作审计，不能把整个父邮件作为所有子任务的有效业务正文。
- 快照来自服务器已确认材料，不依赖临时目录、不随原文件被换名/修改而漂移。通过哈希验证已保存来源；被篡改则拒绝，不静默重读新数据。
- 本阶段建出的任务必须有持久化“尚未开放执行”的明确标记和用户可读原因；可复用现有hold机制或batch_tasks hold，避免仅用RECEIVED导致启动恢复/自动重试立刻执行。明确拦住process/retry/reprocess/补件自动继续/发件箱生成等所有可达入口；不能只在UI隐藏按钮。worker自行设计不影响旧单票的最小方案，必要问题先ask。
- 不连接真实SMTP/IMAP，无可用生产发信开关也不得发信；本阶段不提供释放执行入口。后续阶段再适配process_job消费已确认的分票快照并开放执行。

### 5. 兼容原系统

- 新批次在手工离线入口使用，现有单票收信流程保持兼容；不将新分票识别插入生产poller。
- 明确新批次的多任务邮件关系：batch相关回复若无唯一子任务定位不得路由到任意一票。此阶段可以显式拒绝/引导，不必实现完整批量补件语法。旧有带唯一任务编号/系统通知引用的单票关联保留。
- 生命周期清理/归档、任务详情、查询涉及新增FK/文件引用时必须审查；不会误删共享原件，不让引用链泄露其他票内容。暂不支持的批次删除行为明确拒绝，不静默级联破坏审计。

## 验收测试与交付证据

1. 新库迁移、旧13版升级无数据丢失，旧单票测试保持；不改用户真实数据库。
2. 重复/并发导入同邮件只一批，跨owner/账户或不同原文不混批；预览规则升级不产生新原邮件批次。
3. 方案版本、审计、确认后锁定、过期版本/指纹、未知候选/伪造来源/路径/owner、CSRF、XSS、上传上限等测试。
4. 未归属正文/坏Excel未处理时拒绝；有理由排除留审计；阻断金额/身份冲突不能一键跳过。
5. 双击/并发确认、文件落盘失败、事务中途注入失败、重启后重试：要么完整创建同一组任务，要么零任务/零确认，绝不半批、重复或跳过验证。
6. 每票仅自己的附件/业务正文，输入快照可重开并校验哈希；删除/修改原输入后结果不漂移；候选共享材料边界可验证。
7. 新任务执行hold：poller/recover/retry/process/补件/发送等入口不能绕过；假engine/socket触碰即测试失败。旧单票照常。
8. 三封实际邮件在独立的 runtime/multi-ticket-batches-review/ 下离线导入回放，得到8/1/4候选；有冲突批次保持未确认，不虚构业务决策。不默认确认真实批次；实际建票用合成材料测试证明。
9. Web用TestClient验证完整交互与防护；如能启动仅监听127.0.0.1的隔离无凭据实例，提供实际界面截图（敏感输入仅本地忽略目录），勿启动真实配置服务。
10. 更新 docs/multi-ticket-batches.md，给出CLI/界面用法、状态/表关系、失败恢复和下一阶段边界。运行受影响测试，触及共享task/迁移/邮件路由等需全套回归；配置测试隔离.env。记录命令与通过/失败/跳过理由。

worker_done 必须包含：变更文件、模型和事务边界、如何阻止执行/外发、实际测试命令与结果、8/1/4本地回放位置、未解决限制。不把测试通过当成业务确认。所有有实质业务歧义的事项先通过ask报告并停止依赖该决定的工作，不自动扩大范围。
