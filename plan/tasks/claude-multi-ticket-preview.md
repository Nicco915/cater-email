- 真实输入和研究记录属于敏感商业资料，保持在 input/、output/ 或 runtime/ 的已忽略目录。不要将实际邮件、客户价格、联系人、附件或其复制品放入可跟踪测试 fixture。

## 架构边界

完整路线：邮件审计父记录 -> 输入识别 -> 分票方案 -> 独立任务 -> 逐票执行 -> 批次汇总。本阶段只实现可运行、可检验的“分票预览”，为后续批次/任务持久化留出清晰契约。

1. 核心新增 inspect_sources 或等效独立入口：识别工作簿业务区域与身份、关联正文行、返回候选和冲突。不要让应用层自行另写一套 Excel 结构解析。复用已有只读工作簿加载、安全限制、别名和来源模型；允许必要重构但保持 process_job 单票契约行为。
2. 应用新增离线预览服务与 CLI 子命令：输入本地 .eml（如现有结构适合，也可支持已解析输入），直接生成 JSON 预览，可选显式输出文件。命令必须真正调用新核心入口，无数据库初始化/迁移/写入、无任务创建、无 outbox、无游标变更、无网络、无模板生成。不能走会隐式建库的 AppService 构造路径。
3. 用户可从预览看到候选列表、每票附件/表/区域/正文行来源、识别到的标识、数量和重量、问题及待确认原因。CLI 是本阶段必需交付；不做新 Web 页面，除非现有接口为了兼容有必要的小改动。
4. 不实现正式 fan-out、不做数据库迁移、不接生产 intake、不自动交付。未来新增 mail_batches、batch_tasks/关联表；本阶段不要假装已经有生产多票处理能力。

## 预览契约（可按现有项目风格调整命名，含义必须满足）

- schema_version、规则/识别器版本、来源指纹；不读取秘密。
- candidates[]：稳定 candidate_id、kind、identity（发票/MSO/Order Code/序列号）、source_refs（附件内容哈希、原名、sheet/region）、mail_row_refs、facts（字段值+原始来源）、issues、needs_confirmation。
- 顶层 unmatched_sources/unmatched_mail_rows、issues；单个坏附件可见且不阻止其他候选被展示，但整批不能被误标为全部可执行。
- candidate_id 不能只依赖附件顺序或文件名：相同内容附件改名/调序、重复邮件预览应保持逻辑身份稳定。不要把同发票号当全局永久唯一业务键；若同号内容冲突，应明确报告，不吞掉一个版本。
- 一个 Excel 不必等于一票。不同票分组、同票 CI/PL 分文件组合、相同字节重复附件、多工作表修订冲突需要分别处理；证据不足则保留候选/问题，不猜测。
- 原始正文必须保留审计。仅向单票匹配相关业务行，明确处理引用链历史和重复表，不能让主题压倒附件或首行业务说明。
- 金额有差异要标问题，不擅改价格；重量区分净重/毛重、包装件数/套数。提取不到的字段留空并说明，不填造值。
- 外部输入不可信：拒绝路径穿越、附件超限/坏文件/伪后缀，使用安全文件名；若需临时解包，用隔离临时目录自动清理。不覆盖已有输出或输入；必须有明确覆盖语义才能覆盖指定输出。
